Да, теперь у нас достаточно ТЗ, чтобы **самостоятельно вывести схему**, не меняя твой готовый `schema.sql`.

И я бы пока **не запускал Docker**. Сначала разберём проектирование. После этого станет понятно, что именно мы запускаем и зачем.

## 1. Начинаем с сущностей

В самом ТЗ есть специальный раздел:

> **5. Основные сущности**

И там прямо сказано:

```text
Категория
Лот
Ставка
Пользователь
```

Это первый и самый важный результат анализа.

Значит, у нас будет **4 таблицы**:

```text
categories
users
lots
bets
```

Почему именно они?

Потому что каждая из этих сущностей существует самостоятельно и имеет собственные данные.

Например:

```text
Пользователь
├── email
├── имя
├── пароль
└── контакты
```

Это явно отдельный объект.

А ставка без пользователя и лота сама по себе практически не имеет смысла:

```text
Пользователь ── делает ──> Ставка <── относится к ── Лот
```

Но ставка всё равно является отдельной сущностью, потому что у неё есть собственные данные:

```text
дата
сумма
```

Поэтому:

```text
bets
```

— отдельная таблица.

---

# 2. Категория → `categories`

Смотрим раздел 5.1:

> Категория
> Поля:
>
> * название
> * символьный код

Значит:

```text
categories
├── id
├── character_code
└── name_category
```

Почему появляется `id`, хотя в ТЗ его нет?

Потому что нам нужен **идентификатор записи**.

Например:

```text
id | character_code | name_category
---+----------------+--------------
1  | boards         | Доски и лыжи
2  | attachment     | Крепления
3  | boots          | Ботинки
```

И дальше лот может сказать:

```text
category_id = 2
```

То есть:

> этот лот относится к категории с `id = 2`.

Это и будет связь.

---

# 3. Пользователь → `users`

Раздел 5.4:

> Пользователь
> Поля:
>
> * дата регистрации
> * email
> * имя
> * пароль
> * контакты

Получаем:

```text
users
├── id
├── date_registration
├── email
├── user_name
├── user_password
└── contacts
```

Опять добавляем:

```text
id
```

как первичный ключ.

Теперь посмотри на регистрацию:

> Проверить, что указанный email уже не используется другим пользователем.

Это очень важное требование для проектирования БД.

Email должен быть уникальным:

```text
user 1 → mike@example.com
user 2 → ????
```

Нельзя допустить:

```text
user 1 → mike@example.com
user 2 → mike@example.com
```

Поэтому в схеме появляется:

```sql
email VARCHAR(128) NOT NULL UNIQUE
```

То есть `UNIQUE` мы получили **не из головы**, а непосредственно из бизнес-требования:

> email уже не используется другим пользователем.

# 4. Лот → `lots`

Теперь центральная сущность.

ТЗ говорит:

> Лот
> Поля:
>
> * дата создания
> * название
> * описание
> * изображение
> * начальная цена
> * дата завершения
> * шаг ставки

Получаем:

```text
lots
├── id
├── date_creation
├── title
├── lot_description
├── img
├── start_price
├── date_finish
└── step
```

Пока всё просто.

Но дальше ТЗ говорит:

> Связи:
>
> * автор: пользователь, создавший лот;
> * победитель: пользователь, выигравший лот;
> * категория: категория объявления.

Вот здесь начинается самое интересное.

---

# 5. Автор лота

У нас есть:

```text
users
```

и:

```text
lots
```

Один пользователь может создать много лотов:

```text
Пользователь №1
   │
   ├── Лот №1
   ├── Лот №2
   └── Лот №3
```

Следовательно:

```text
users 1 ──────── N lots
```

Как хранить эту связь?

**Не надо добавлять в `users` список лотов.**

Вместо этого добавляем в `lots`:

```text
user_id
```

Получается:

```text
lots
├── id
├── ...
└── user_id
```

И `user_id` должен ссылаться на:

```text
users.id
```

Поэтому:

```sql
FOREIGN KEY (user_id) REFERENCES users(id)
```

Теперь запись:

```text
lots
id = 15
user_id = 3
```

означает:

> Лот №15 создан пользователем №3.

---

# 6. Победитель

Теперь ещё одна связь между `lots` и `users`.

ТЗ говорит:

> победитель: пользователь, выигравший лот.

И алгоритм определения победителя говорит:

> Записать в лот в качестве победителя автора последней ставки.

То есть у лота может появиться пользователь-победитель.

Получается ещё одна связь:

```text
users 1 ──────── N lots
       автор

users 1 ──────── N lots
       победитель
```

Это **две разные связи между одними и теми же таблицами**.

Поэтому одного `user_id` недостаточно.

Нужен второй:

```text
winner_id
```

И:

```sql
FOREIGN KEY (winner_id) REFERENCES users(id)
```

Теперь:

```text
lots
├── user_id    → кто создал
└── winner_id  → кто выиграл
```

Это очень хороший пример того, почему имя внешнего ключа важно: оба поля указывают на `users`, но означают совершенно разные отношения.

# 7. Категория лота

ТЗ говорит:

> Каждый лот должен быть привязан к одной категории.

То есть:

```text
Категория 1
   │
   ├── Лот 1
   ├── Лот 2
   └── Лот 7
```

Получается:

```text
categories 1 ─────── N lots
```

Следовательно, внешний ключ должен находиться в `lots`:

```text
category_id
```

И:

```sql
FOREIGN KEY (category_id) REFERENCES categories(id)
```

Теперь `lots` полностью выглядит концептуально:

```text
lots
├── id
├── date_creation
├── title
├── lot_description
├── img
├── start_price
├── date_finish
├── step
│
├── user_id       → users.id
├── winner_id     → users.id
└── category_id   → categories.id
```

И вот мы уже практически получили твою таблицу `lots`.

# 8. Ставка → `bets`

Раздел 5.3:

> Поля:
>

> * сумма

Получаем:

```text
bets
```

```text
            │ id                     │◄────│ lot_id   │

            │ lot_description        │
```

# 10. Откуда взялись типы данных?

Вот здесь начинается следующий уровень проектирования.

Мы уже определили **что хранить**. Теперь надо решить **как хранить**.

Например:

### `id`

Нам нужен целочисленный идентификатор:

```sql
id INT AUTO_INCREMENT PRIMARY KEY
```

`AUTO_INCREMENT` означает:

```text
1
2
3
4
...
```

MySQL сам выдаёт следующий ID.

---

### Дата и время

ТЗ говорит:

> дата и время

Поэтому:

```sql
TIMESTAMP
```

Например:

```text
2026-09-10 11:30:25
```

И для даты создания:

```sql
date_creation TIMESTAMP DEFAULT CURRENT_TIMESTAMP
```

То есть MySQL сам поставит момент создания записи.

---

### День окончания

ТЗ говорит:

> дата завершения

Причём форма требует:

```text
ГГГГ-ММ-ДД
```

Поэтому:

```sql
DATE
```

а не `TIMESTAMP`.

Получаем:

```sql
date_finish DATE
```

---

### Название

Текст ограниченной длины:

```sql
VARCHAR(255)
```

---

### Описание

Описание потенциально длинное:

```sql
TEXT
```

---

### Изображение

В БД хранится **не само изображение**, а ссылка на него:

> сохранить ссылку.

Поэтому:

```sql
img VARCHAR(255)
```

---

### Цена

В ТЗ цена — целое положительное число:

```text
начальная цена
шаг ставки
ставка
```

Поэтому в этом учебном проекте:

```sql
INT
```

Получаем:

```text
start_price INT
step        INT
price_bet   INT
```

# 11. Откуда взялись индексы?

Теперь возвращаемся к требованиям урока:

> Поля для хранения уникальных значений должны иметь индекс типа `UNIQUE`.

У нас есть явное требование:

> email не должен использоваться другим пользователем.

Поэтому:

```sql
email VARCHAR(128) NOT NULL UNIQUE
```

И второе:

```text
character_code
```

Символьный код категории должен быть уникальным, потому что иначе мы получили бы:

```text
boards → Доски и лыжи
boards → Ботинки
```

и уже нельзя было бы однозначно использовать код.

Поэтому:

```sql
character_code VARCHAR(128) UNIQUE
```

---

# 12. А почему нет `INDEX` на всём подряд?

Вот здесь важно не сделать ошибочный вывод:

> «Если поле участвует в поиске — надо поставить индекс».

Индексы нужны с учётом **реальных запросов**.

Например, ТЗ говорит:

> поиск по названию и описанию с использованием полнотекстового поиска `MATCH ... AGAINST`.

Для такого поиска в MySQL обычно нужен **FULLTEXT index**.

Но твой предоставленный `schema.sql` его не содержит.

И здесь я специально **не буду его добавлять**, потому что наша цель сейчас — не исправлять решение курса, а понять, как автор задания пришёл именно к этой схеме.

Это хороший момент для обучения: **ТЗ → требования → схема**, а не «современная оптимальная схема любой ценой».

# 13. И теперь можно буквально прочитать `schema.sql`

Первая часть:

```sql
DROP DATABASE IF EXISTS yeticave;

CREATE DATABASE yeticave
  DEFAULT CHARACTER SET utf8
  DEFAULT COLLATE utf8_general_ci;

USE yeticave;
```

означает:

```text
удалить старую БД
       ↓
создать новую БД
       ↓
переключиться на неё
```

А затем:

```sql
CREATE TABLE categories
```

потому что мы нашли сущность **Категория**.

Потом:

```sql
CREATE TABLE users
```

потому что нашли **Пользователь**.

Потом:

```sql
CREATE TABLE lots
```

потому что нашли **Лот**.

И здесь появляются внешние ключи:

```sql
FOREIGN KEY (user_id) REFERENCES users(id),
FOREIGN KEY (winner_id) REFERENCES users(id),
FOREIGN KEY (category_id) REFERENCES categories(id)
```

потому что ТЗ описало три связи.

И наконец:

```sql
CREATE TABLE bets
```

потому что **Ставка** — отдельная сущность.

И:

```sql
FOREIGN KEY (user_id) REFERENCES users(id),
FOREIGN KEY (lot_id) REFERENCES lots(id)
```

потому что ставка связана с пользователем и лотом.

## То есть главное, что тебе нужно сейчас понять

Проектирование БД — это не:

> «Я знаю SQL, сейчас накидаю `CREATE TABLE`.»

А наоборот:

```text
             ТЗ
              │
              ▼
       Что существует?
              │
              ▼
          Сущности
              │
       ┌──────┼──────┐
       ▼      ▼      ▼
    User     Lot    Bet ...
       │
       ▼
    Какие данные?
       │
       ▼
      Поля
       │
       ▼
   Как связаны?
       │
       ▼
    FK / PK
       │
       ▼
 Что должно быть уникальным?
       │
       ▼
     UNIQUE
       │
       ▼
 По чему ищем?
       │
       ▼
     INDEX
       │
       ▼
      SQL
```

**Именно поэтому твой `schema.sql` выглядит так, а не иначе.**

```text
     │
```

А уже после создания контейнера покажу тебе **два способа выполнить `schema.sql`: через терминал и через встроенный Database-инструмент PhpStorm** — и объясню, что физически происходит при каждом варианте.
